Code that contradicts this document is a bug either in the code or in the document; the latter is fixed by editing this file, never silently in code. ## What we are building

Quorum is a multi-agent system that, for one event, collects publications from different sources, separates facts from interpretations, verifies claims against evidence, and shows how different parts of the political spectrum frame that event.

**Motivation.** Societies are polarized, and everyone lives in their own information bubble. A Democrat does not see the facts a Republican sees, or does not weigh them. A Republican, the other way round. Instead of one source with its interpretation, the user gets the fact: what happened. On request, statistics on how a given party or outlet interpreted that fact.

**Key feature.** Quorum does not retell the news. It investigates what is actually known, which claims contradict each other, what evidence exists, and how different sources interpret the same event. The goal is an AI that does not ask the user to trust its answer, but lets them verify every substantive conclusion.

**Context.** Team Quorum's project for the [Open Agent Hackathon 2026](https://hackathon.genai.works/event/open-agent-hackathon-2026), Track 03 Reasoning Architecture. Build window 22–27 October 2026; submissions close 27 October 23:45 UTC (19:45 New York). The judges expect an agent system with verification loops, not a linear pipeline.

## MVP scope

The MVP consists of the six features from the agreed project description plus seven team decisions: topic selection, login, an independent fact-checker, four spectrum-rating modes, selection of stories by an absolute impact bar, stories written as articles, and the "Also today" roundup.

| Feature | What it includes |
| --- | --- |
| 1. Multi-source intelligence | News from several independent sources: RSS, news APIs, official publications. Federated through Zetaris with SQL queries across sources. Grouping of publications about one event. |
| 2. Autonomous fact verification | The AI extracts checkable claims, looks for supporting and contradicting evidence, and requests additional sources when needed. It distinguishes confirmed facts, disputed claims, and what cannot yet be verified. It accounts for several publications retelling one primary source. |
| 3. Evidence-based reasoning | Every conclusion carries its sources and an explanation of the evidence it rests on. When sources contradict each other, the agent investigates the cause of the discrepancy. When evidence is insufficient, the system says so plainly. The user sees the verification process and can go to the originals. |
| 4. Neutral news brief | A short article (3–4 minutes) built only from verified claims, without political interpretation or evaluation. What happened, what the parties say and what is not confirmed are kept apart by writing rules, not by headings (see "Stories as articles"). |
| 5. Narrative & framing comparison | How different sources cover one event: which facts they highlight, which they omit, which wording they use. Comparison of specific outlets and statements by political organizations. Every conclusion comes with examples from the source material. |
| 6. Interactive dashboard | Event feed and topic filter. Event page with facts, sources and disagreements. Comparison of coverage across sources. Drill-down into evidence and reasoning. |

**Added by team decision**

- Topic selection at first setup: the agents collect and analyze only those topics.
- Login and password. No subscription; free at first.
- An independent fact-checker in addition to cross-checking publications (see "Principles for handling facts").
- Four political-spectrum rating modes and a cohort diagram (see "Spectrum ratings and cohorts").
- Stories are selected by an absolute impact bar, up to ten a day per topic and with no minimum; coverage and silence per cohort are a separate fact (see "Selecting major news").
- Stories are written as short articles with photos, not as briefs with headings; facts only, no evaluation (see "Stories as articles").
- An "Also today" roundup per topic and day: one line for every event below the bar, with its source and status (see "Selecting major news").

**Out of scope:** social networks (Facebook and others) — many bots, an unrealistic picture, and questionable legality of collection. Sources are news outlets and official government bodies.

## Principles for handling facts

A fact is either a signed document or a claim confirmed by independent sources. Everything else is a statement and is presented as a statement.

- **Statement = a party's words. Signed document = fact.** A decree, law, order, court ruling or signed agreement is a fact. Operationally: the fact is that the document was adopted and what it says. Assessments and figures inside the document about the outside world remain the signer's claims. Otherwise any defense ministry's report would automatically become a fact.
- **Official government documents are the top-priority source.** Media news is not. The model does not guess: a claim without a source is not accepted.
- **Two metrics that are never mixed.** "Confirmation" counts only independent sources: ten reprints of one wire story are one piece of evidence, not ten. The outlet or agency a claim was first reported by counts as one of its independent sources when it speaks about others, never about itself: the origin plus one other independent source confirm (decided 2026-10-24). "Spread" counts without deduplication: every publication is separate, because people read it.
- **A corrected publication is not evidence.** A document another row supersedes (`supersedes_id`) is excluded from evidence, confirmation and claim extraction. A supersede chain (one URL re-fetched with a changed hash: a live blog, an edited article) is one publication for spread and coverage, represented by its newest row; the superseded versions stay visible in the trace only (decided 2026-10-24, chain-once rule; supersedes the same-day wording "stays in spread and coverage").
- **Independent fact-checker.** A separate agent re-verifies the extracted claims without seeing the primary verifier's conclusions. A different model, if the hackathon rules allow, and its own toolset: search over primary sources and official documents. A disagreement between the two checks goes to a third blind reviewer (adopted 2026-10-24, implemented after the first live run): a different model when available, both evidence chains as input, one pass, no new evidence; if the reviewer validates one chain under the confirmation rule, that verdict stands and the trace shows all three; otherwise "disputed". Never resolved by guessing: the code rule, not the vote, still gates "confirmed". Until the reviewer exists, a disagreement = "disputed".
- **A contradiction must be grounded (2026-10-25, Yelysei).** A passage counts as contradicting a claim only when the stance model quotes, verbatim from that passage, the words that assert the opposite of the same fact about the same actors, place and time, and the code finds those words in the passage; otherwise the answer is treated as "about something else". A caption, navigation text, another incident or another day is never a contradiction. The quoted words must be a whole clause (five words or more) or, when the contradiction is a number, a date or a denial, the short phrase that carries it (two to four words with a digit, a date word or a negation); a two-word run alone is too easy to rip out of context (refined 2026-10-25, Yelysei). A contradiction must also be about the same fact, not merely the same topic (2026-10-25, Yelysei): the passage together with its context window (two sentences before and after, which the model also receives with the document title to judge whether it is the same event) must cover at least 40% of the claim's fact composition (its significant word stems minus the topic's most frequent ones, excluded only when the run has 30 or more documents), at least two stems, with a lower 25% bar for the short number/date/negation phrases; and when both the claim and the passage state a date, the dates must agree unless the quoted span is itself the date. A shared name ("Trump") never suffices. A support is held to the same rule as a contradiction (2026-10-25, Yelysei, decided in the night regime and confirmed by him the same day; the lighter one-stem version of the same day is superseded): the model quotes verbatim the words of the passage that state the same fact, the quote must share two stems of the claim's fact composition, and the passage with its context window must cover the composition like a contradiction's (same bars, floor, fallback and date rule); otherwise the answer counts as "about something else". Why: on the first run under the lighter rule the noise moved from "disputed" to "confirmed" (about 8 of 14 roundup "Confirmed" labels rested on passages about something else); on the same journal the stricter rule keeps the obviously true supports (the Oleshky truce, the 29 October start) and drops loosely worded ones on long claims, which is the accepted cost. Why: on a live probe the model called an unrelated strike report a support of a satellite-service claim, and a support feeds confirmation, which has no other guard than the two-group rule. Short contradiction quotes of two to four words also pass when they share two fact-composition stems with the claim. Passages that share almost no words with the claim are not sent to the model at all (a cost guard, `research.stance_min_overlap`). Why: on the first canonical run the model labelled photo captions and unrelated passages "contradicts", and one such label makes a claim disputed against two independent confirmations; "disputed" had become the dominant roundup label (12 of 26 events). The confirmation rule itself (one grounded contradiction → disputed) is unchanged.
- **Sources under every conclusion.** The agent explains why a claim was accepted as real rather than fake, and provides links. If evidence is thin, the system says so plainly instead of inventing an answer.

## Spectrum ratings and cohorts

A source's position on the spectrum comes from external ratings in one of four modes. Switching the mode recomputes the center and the cohorts.

- Modes: [AllSides](https://www.allsides.com/media-bias/ratings), [MBFC](https://mediabiasfactcheck.com/), [Ad Fontes](https://adfontesmedia.com/) and averaged.
- The averaged mode uses an open formula. Each rating is mapped to a −1…+1 scale: AllSides (5 steps) → −1, −0.5, 0, +0.5, +1; MBFC (7 steps) → −1, −0.67, −0.33, 0, +0.33, +0.67, +1; Ad Fontes → bias ÷ 42. The result is the mean of the available ratings.
- Cohorts by threshold: ≤ −0.25 left; between −0.25 and +0.25 center; ≥ +0.25 right. The formula is shown in the tooltip of the mode switch.
- Ratings for ~40 sources are entered by hand into a CSV, not scraped.
- The model's own spectrum rating is not used in the MVP (see "After the hackathon").

$$
s = \frac{1}{n}\sum_{i=1}^{n} s_i,\qquad s_i \in [-1,\,1],\qquad n = \text{number of available ratings}
$$

**Diagram and cohorts.** X axis: position under the selected rating mode. Y axis: audience, log scale. Four cohorts: major left, major right, minor left, minor right. Per-cohort statistics: share of outlets and share of audience. This makes visible the concentration of the right around a few major outlets and the spread of the left.

| Audience ↓ / Position → | Left | Right |
| --- | --- | --- |
| **Major** | CNN, NYT, Washington Post, Guardian, NPR, MSNBC, HuffPost | Fox News, NY Post |
| **Minor** | Vox, Mother Jones, The Intercept, Salon, The Atlantic, The Daily Beast, Slate, The New Republic, The Nation, Common Dreams | Washington Examiner, Washington Times, Daily Caller, Daily Wire, Newsmax, Washington Free Beacon, The Federalist, Breitbart, The Blaze, Townhall, National Review, The Daily Signal, RedState |

## Stories as articles

A story is a short article the reader can form their own view from: facts with sources, the parties' statements with their authors, and what is not confirmed. No evaluation is added. The three parts of the brief stay as data and as rules for the critic; on the page they are prose, not headings.

- **Built only from verified claims.** Every sentence maps to a claim with a status. The writer cannot add a sentence that has no claim behind it, and the critic rejects any that does.
- **Status is shown by typography, not by sections.** A confirmed fact is plain text with its sources in small gray links right after the sentence. A statement is attributed in the sentence itself ("the White House says"). What is not confirmed is a short paragraph at the end, "Not confirmed". One gray line under the headline explains this key.
- **No evaluation.** Forbidden in the writer's voice: evaluative adjectives and adverbs, predictions, causal links without a source, and any "why it matters". What an event may change is for the reader to decide or for the parties to claim, with attribution.
- **Context only as facts.** Prior comparable events, the document's own provisions, numbers from official data — each with a source. "The previous package took eleven weeks to ship" is context; "this one matters because it is a law" is not.
- **Fixed order:** facts in chronological order, then statements, then what is not confirmed. A fixed order removes framing by sequence.
- **Headline and standfirst.** Headline: subject, verb, object, no adjectives. Standfirst: three facts.
- **Length:** 2–4 minutes of reading. The writer picks one of a few shapes by event type (event report, document explainer, dispute explainer); the shapes are few so the critic can check them.
- **Photos.** One lead photo and at most one inline photo, only when the agent finds a suitable image under an allowed license: US federal government sites (public domain) and Wikimedia Commons with an open license. Always with a credit and a caption that says what is shown, without adjectives. No photo is fine. AP, Reuters and AFP photos are not used. A photo is also framing: documentary and official images, not emotional ones.
- **At the end, as an appendix:** "Across the spectrum" — how left and right outlets told the story, one line on where big and small outlets differ, and links to all claims with evidence and to the reasoning trace. A reader who wants only the facts never reaches it.

## Selecting major news

Importance is measured by impact on people's lives, not by how many outlets covered an event. Ten stories a day per topic is a cap, not a target: a day with three stories shows three, a day with none says so.

- **Candidates** are all events in the corpus, including official documents. An event nobody published cannot be seen by the system. The realistic case is "covered only by government bodies or by one or two sources". Amended 2026-10-26 (Yelysei): an official document starts an event only under the seed rule in "Sources" (a term of the topic in its title or abstract); any other official document is evidence only: it may join an event another document started, but it starts none and is never a roundup item by itself.
- **An absolute bar, not a ranking.** A top-N always produces N. Instead each event is scored on an open rubric and shown only if it crosses a fixed threshold: legal force (0 none, 1 official statement, 2 adopted document); reach (0 local or unknown, 1 a region or one sector, 2 national or several sectors, 3 several countries — an event with confirmed deaths or mass displacement reaches the whole country, 2, wherever it happened); irreversibility (0 reversible, 1 hard to reverse, 2 irreversible); confirmation (0 unverified, 1 one independent source, 2 two independent sources or a document). A story is shown when the total is at least 6 and confirmation is at least 1. The threshold is a configuration parameter and is calibrated on the first real days.
- **Two rubric points are derived from facts, not scored (2026-10-25, Yelysei).** The model does not score legal force and irreversibility; it reports two checkable facts with a rationale naming what in the documents shows them: the legal status (nothing binding / an official statement, announcement or proposal / an adopted, signed, voted or ruled document) and the state of the act (announced, proposed, threatened or conditional / adopted but undoable by a later act / carried out with physical or legal finality). Code maps them to the 0–2 points; an unreported or unrecognised fact scores 0 (below the bar, never above). Reach stays the model's judgement. Why: on the first canonical run the only story reached the bar on an irreversibility point of 1 whose own rationale said "conditional and reversible" (0 on the scale); with the facts mapped by code the event is gated and the day has no story. A score and a free-text rationale cannot check each other; a fact and a mapping can.
- **Confirmation is a gate.** An unconfirmed event never becomes a story, however large its potential impact; it goes to the roundup marked "reported, not confirmed".
- **"Interesting" is not a criterion.** Only the rubric decides; liveliness follows from impact.
- **The bar gates the expensive checks (2026-10-24, Yelysei; measured on the first two genuine runs).** After the rubric is scored, an event whose three judged points plus the maximum confirmation score (2) still fall short of the threshold cannot become a story whatever the evidence shows. For such an event the claims still get both research rounds on the fast lane (so the roundup label rests on the day's documents, official documents and the previous days), but the blind fact-checker and the reviewer (the large model) are skipped: each claim is exported with `fact_checker: unverified` and a reason "skipped: event cannot reach the bar", its status is the verifier's verdict, `resolved_by` is omitted, and the adjudication says "not double-checked". Events that can reach the bar keep the full chain. Why: on 2026-10-24 no event could reach the bar and 77% of the run's model calls (all of the large-model calls) bought only roundup labels; a roundup label is not a published fact and does not need the two-checker guarantee that a story's fact block needs. An event whose scoring call failed scores 0 and is gated as well (score.py fails below the bar, never above). Consequence for the portal: roundup labels of below-bar events ("Confirmed", "Disputed") rest on one checker; the claims of such events are not exported (roundup items carry no claims), so the only visible mark is the trace row `fact_check … skipped`. Gated events also carry no fact-checker evidence, so their confirmation points, rubric total and roundup order can be lower than with the full chain.
- **No minimum.** A day with no story above the bar is stated plainly on the topic page and on the home card: "No story crossed the bar today". The roundup then carries every event of the day.
- **"Also today" roundup** — one article per topic and day for everything below the bar: one line per event with its source and status (confirmed, disputed, statements only, single source, and unverified as the label of last resort — several sources, no confirmed or disputed claim, not only statements), grouped by sub-topic, ordered by rubric score. It includes events covered only by official sources. No framing analysis for roundup items.
- **Coverage and silence per cohort** is a separate, visible fact: "covered by N of M sources in the cohort". A whole cohort's silence on a story is a highlighted line.
- **The rule is visible.** The topic page carries a short "What crosses the bar" note; the full rubric score for each story is in its trace.

- Access levels: 1 — full text; 2 — headline and lead from RSS; 3 — only the fact of coverage. Paywalled sources participate at level 2 and their scores are marked "by headline". A domain whose robots.txt disallows our crawler drops to level 2 automatically.
- Full article text is never stored. The `documents` table keeps title, lead, URL and a content hash; reasoning reads the text at analysis time and stores only verbatim quotes with character offsets (`quotes`). Government documents (`official_docs`) are stored in full: they are public domain. Schema and module rules: `collectors/README.md`.
- Collection delivers a flat stream of documents tagged with topics; event ids and clustering are assigned by reasoning. Confirmation excludes wire reprints (`wire_origin`); coverage counts every publication.
- **Official documents: seed rule (2026-10-26, Yelysei).** In reasoning an official document of the edition window seeds an event only when a term of the run's topic (`topics.query_terms`) occurs in its title or its abstract, matched the way collection matches documents: whole word, case-insensitive, no stemming (`collectors/common.py` `matches_topic` / `topic_match_of`; reasoning's copy with pinned test vectors is `reasoning/quorum_reasoning/topic_match.py`). The abstract is the Federal Register's SUMMARY paragraph when the stored text has one, read whole across a page break (the `[[Page N]]` markers and the blank lines around them are removed first). A Federal Register page without a SUMMARY (the stored text carries the Federal Register page header, `[FR Doc No: ...]`) has no abstract, as the Federal Register API's abstract is null for those documents, and is matched on its title alone (presidential documents, Sunshine Act and filing notices: their opening is the issue's cover page listing the other documents of the same Part, an order's enacting clause or a meeting agenda). A `federal-register` row without the page header is the API's abstract itself (collection stores the API's `abstract` as the text when a document has no raw text URL, and skips a document with neither) and is read whole, up to 4 000 characters. For other sources the abstract is the text's first 600 characters (a bill's title, latest action and summary; a release's opening), with an order's "By the authority vested in me ...:" clause left out. Every other official document stays evidence only: research round 2 and the fact-checker may quote it, and it may join an event that an outlet document or a seed-eligible official document started (clustering keys it with the window's other documents, drops every group with no such member and asks no merge question where neither side has one), but it starts no event and is never a roundup item by itself. Review round 1 (2026-10-26, Claude Code) superseded two parts of the first version of this entry: "joins none" (Claude Code's reading, not the owner's rule) and the first-600-characters abstract for a Federal Register document without a SUMMARY. Review round 2 (2026-10-26, Claude Code) superseded round 1's test of "a Federal Register document" by its source alone (`federal-register`): only the page header says a document has no abstract, since a headerless `federal-register` row is the API's non-null abstract and was matched on its title only; all 256 `federal-register` rows of the rehearsal dump carry the header, so no verdict over its 295 official documents changes. When the topic's row is missing or its terms are empty or unreadable, no official document seeds an event and the plan trace row says why; a failed lookup is also a run error (`partial`). The plan trace row counts official documents: total, seed-eligible (title / abstract), evidence only. The fixture corpus keeps every official document as a seed and its plan trace row as before (no official-document counts), so a fixture dry run still reproduces the committed samples in `docs/examples/`. Why: collection's Federal Register query matches a multi-word term as an implicit AND of its words over the whole text, so unrelated notices were collected under the topic and became events; dry runs on the rehearsal dump (edition 2026-10-26): ai-regulation-export-controls 10 of 15 roundup items were official notices ("Ohio Regulatory Program" labelled Confirmed) and at least 270 of 417 stand-in calls went to those events (merge questions not counted); russia-ukraine-war 1 of 12 ("Prestressed Concrete Steel Wire Strand From Spain"); federal-budget-shutdown 4 of 4. With the rule: 0 of 5, 0 of 11 and 0 of 0 (65, 194 and 1 stand-in calls). Review round 1, over all 295 official documents of the dump: 3 of the 4 documents seed-eligible only through the 600-character fallback matched boilerplate (official_docs 5934 and 5898 on "section 301" in the enacting clause "section 301 of title 3, United States Code", 6215 on "Fiscal Year 2027" in a Sunshine Act agenda), and 8 SUMMARY paragraphs were cut at a page break (6108 lost "southern border" and so did not seed immigration-southern-border); with the fixes 75 of the 295 are seed-eligible for their topic (77 before) and 46 Federal Register documents are matched on their title alone. Dry runs after review round 1 (edition 2026-10-26; events / roundup items / stand-in calls, no event made only of evidence-only documents): ai-regulation-export-controls 5 / 5 / 77, russia-ukraine-war 11 / 11 / 195, federal-budget-shutdown 0 / 0 / 1 (no seed document, nothing clustered), tariffs-trade-war-china 7 / 7 / 69 (one seed-eligible official document, by title, is an event and a roundup item of its own), immigration-southern-border 17 / 17 / 239, climate-policy 2 / 2 / 24; in none did an evidence-only document join an outlet event. Known consequences, for the owner to weigh: a term only in the body does not seed (Treasury's Outbound Investment proposed rule names artificial intelligence 9 times, never in its title or summary), and a trade-remedy notice naming a country of the topic in its title still seeds (11 of the 14 seed-eligible russia-ukraine-war official documents in the dump are trade-remedy notices listing Ukraine among the countries); evidence-only documents still take round-2 stance calls (17 of 32 in the ai-regulation dry run); a Federal Register page without a SUMMARY, an executive order or proclamation included, seeds only by its title; every evidence-only document of the window costs one event-key call (12 more in the ai-regulation dry run, 65 to 77 stand-in calls), while the 66 merge questions between evidence-only documents there are not asked (the pair pass may spend 120 of the 160; before the rule 73 pair questions were asked, 66 of them between such documents); an evidence-only document that joins an outlet event is a member like any other (judged in research round 1, may give the event claims and its legal status, listed among the roundup line's sources) and, being official, is preferred as the event's headline (`cluster._representative`).
- An outlet's flank comes from the external ratings in the selected mode, not from the team's taste. Tier comes from audience; for the MVP the majors are a fixed list.
- Audience figures for the Y axis and cohort shares are public estimates, entered by hand into the CSV.
- Social networks are out of scope.

## User account and interface

The account is built around the topics the user selects. The interface is simple in the manner of Apple News: a few readable elements beat many metrics. Numbers and analysis live behind links, never on the first screen. A design mock of all screens exists as a Claude Design canvas, "Quorum — app screens" (Yelysei's account; ask for a share link).

1. **Sign-in.** Login and password. No subscription; free at first.
2. **First setup.** The user picks the topics they care about. The agents collect and analyze only those.
3. **Home.** One card per topic, like Apple News: a photo of the day as background, the topic name in a large rounded display font over it, one line with the lead story and the number of stories today (or "No story crossed the bar today"), a small photo credit. The first topic is a full-width card, the rest a two-column grid.
4. **Topic page for today.**
    - One paragraph: how many events crossed the bar and how the views of different parties are distributed.
    - The stories that crossed the bar (up to ten): number, headline, a one-line factual standfirst with reading time, a thumbnail. A whole cohort's silence is one red line under the story.
    - A card to the "Also today" roundup, naming what is in it.
    - Aside: the lead story's interpretations in words ("19 outlets, mostly left"); who counts as left and right, with the rating-mode switch as a text link; a three-sentence "What crosses the bar" note.
5. **Story page** — the article (see "Stories as articles"), then "Across the spectrum" as an appendix.
6. **Roundup page** — "Also today": one line per event below the bar, grouped, with source and status.
7. **History** — a tab on the topic page, by day, labeled like "digest for 10/12/2026".
8. **Shift in party positions** — under the topic, outside the days. Implemented after the hackathon; data accumulates from day one.
9. **Type and color.** Display: SF Pro Rounded via the CSS generic `ui-rounded` (Safari, iOS), with Nunito from Google Fonts as the fallback elsewhere. Body: the system font, with Inter as the fallback. White background, one red accent for the date, cohort colors blue (left) and red (right), darker for big outlets and lighter for small ones. Status words, not colored pills.

## Stack and work blocks

Data flows through Zetaris and reasoning runs on NVIDIA Nemotron and Meterless. The user-facing frontend is Next.js + TypeScript; Django owns authentication, user management, administration and web-facing API endpoints.

Previous stack decision (superseded 2026-10-22 by explicit human team-approved clarification): interface and backend both used Next.js + TypeScript. Collectors and reasoning ownership and architecture are unchanged. The architecture is an agent system with verification loops, not a linear pipeline; its detailed design is a separate task on the board.

## Daily editions for users: topics, delivery time, where runs execute

Decided 2026-10-25 (Yelysei; asked for by Vadim before any scheduling is built; collection side agreed in Issue #2 6394199167):

- **Topics are free text.** The user types a topic; the web app writes a `topics` row (slug, name, query terms) that the collector reads at the start of every pass (no rebuild). Reasoning turns the user's words into whole-word query terms (`python -m quorum_reasoning.topics --suggest`), with a deterministic fallback so a topic can always be created. A new topic's first edition is thin until feeds accumulate; the UI says so instead of hiding it.
- **Typed-topic intake (2026-10-26).** The web app stores what a reader types as a request `{key, text, count}` (no user data in the batch) and never calls a model; the operator runs `python -m quorum_reasoning.topics --from-requests requests.json --out DIR [--dry-run]`, which reads the existing topics through Zetaris (read-only; a read that yields no topic with an id fails the batch with exit 2 and nothing written, since collection always holds its seed topic and zero topics means a misread; an explicit `--existing` file may be empty) and writes `mapping.json` (each request → `existing` | `new` | `needs_review` | `rejected`, with topic id, name, terms, conflicts and reason, and a `caution` for terms derived from the phrase), `rows.sql` (the new rows only) and `report.txt`; the web app or the operator applies `rows.sql` to collection's database. Agents run it with `--dry-run` only (deterministic terms, no model call).
  - **Request key, the contract with the web app** (2026-10-26; agreed with the web side in Issue #2 6411408519 item 1, adopted by reasoning in 6411653104): NFKD fold, lowercase, every run of non-letters/non-digits → one space, drop one-letter tokens, drop the stopwords `the a an of in on and or for to vs v at by with` (this list, nothing more), then the sorted unique tokens joined by single spaces. The shared definition is the web app's `words()` in `web/lib/topic-search.mjs` (PR #24), and the key is `[...new Set(words(text))].sort().join(" ")`; reasoning's copy, `topics.request_key`, gives the same string byte for byte, so the details are the web code's: lowercase (`toLowerCase`) before NFKD, then only U+0300–036F deleted; letters and digits are Unicode categories L and N, so everything else separates words (apostrophes, full stops, format characters such as a soft hyphen, and combining marks outside U+0300–036F such as Indic and Thai vowel signs); a one-letter token is one UTF-16 code unit; the sort is JavaScript's default `sort()` (UTF-16 code units). Shared test vectors for both sides: `reasoning/tests/data/topic_key_vectors.json` (`[{"text", "key"}]`; a reasoning test runs the web file over them with node). "war in Ukraine" and "Ukraine war" → `ukraine war`; "U.S. tariffs on China!" → `china tariffs`; "चीन" leaves only one-letter tokens, an empty key, and is rejected. The intake groups and matches requests by the key of the text after deleting format characters (Validation), and checks the web app's `key` against the key of the text as sent. *Superseded 2026-10-26 (closing round 4): the key this branch had before, proposed by Claude Code (its narrower diacritic folding in review round 2) and never confirmed: delete format characters (Unicode category Cf) → lowercase → Unicode NFKD → delete the combining diacritics (U+0300–036F, U+1AB0–1AFF, U+1DC0–1DFF, U+20D0–20FF, U+FE20–FE2F; other combining marks, such as the vowel signs of Indic and Thai scripts, stayed) → lowercase; delete a full stop between two letters; tokens = runs of letters, marks and digits; drop the stopwords `a about an and at by for from in into of on or over s the to vs with news`; the unique tokens sorted by code point; "चीन" (China) and "चना" (chickpea) were two keys; a JavaScript twin in `topics.request_key`'s docstring.*
  - **Validation** (the web app runs the same checks before it stores a request; the batch repeats them): format characters (Cf) are deleted first (the key itself does not delete them; the batch keys the text after this deletion); at most 80 characters after collapsing whitespace; not empty after normalising; at least one letter; no URL (a scheme, `www.`, a dotted name ending in a common TLD, or a dotted name whose last label starts with a letter followed by `/`; the labels may be in any script and `。` `．` `｡` count as dots: `jаnedoe.com/profile` with a Cyrillic `а`, `münchen.de/news`, `пример.рф/ivan-petrov`, `example。com/jane`), no e-mail address (any word@word, no dotted domain needed), no other `@` (a handle; a typed topic never needs one) and no phone number (`+` and a run of digits and separators, a North American or a 7-digit local number (3 and 4 digits, also when a word is joined to it by `-`, `.`, `/`, `_` or a dash, or a full stop ends it: `jane-555-1234`, `call 555-1234.`, or another digit group is joined to it: `call 1-555-1234`; not inside a longer run of digits; not when a space separates the 3 and the 4 digits, as in `Fortune 500 2026`), or a run of digits and separators holding 9 or more digits, however many groups, every dash-like character, `/` and `_` counting as a separator: `555‑123‑4567` with a non-breaking hyphen, `555/123/4567`, `0170 1234567`, `07911123456`, `123456789`; not `2024-2025` or `Boeing 737-800`), these personal-data patterns matched on the NFKC form of the text (rejected, and their text is withheld from every output, a text of digits alone too); a `key` the web app sends that differs from the contract's key is scanned with the same patterns and written as `[withheld]` when one matches or it is over 80 characters (`key_mismatch` still gives the contract's key); no `<`, `>` (also looked for in the NFKC form, so full-width `＜` `＞` count), control characters (C0 except tab, newline and return; DEL; C1) or private-use, unpaired-surrogate or unassigned code points (categories Co, Cs, Cn). Exact patterns: `topics.check_request`. A proposed row (the model's reply on the live path, derive's otherwise) passes the same personal-data checks before any of it is written: a name that fails `check_request` is replaced by derive's name of the typed text; when the name was replaced, or the proposed slug matches the personal-data patterns, the id is derive's slug of the typed text, and `topic-<hash>` when that matches them too. Derive's slug of the typed text joins the typed words with `-`, so it is scanned with its hyphens read as spaces, as the typed text was (`fortune-500-2026` of "Fortune 500 2026", `section-230-2026`, `jane-doe-555-1234` of "Jane Doe 555 1234" stay; `2026-2027-100-plans` of "2026 and 2027 and 100 plans" holds 11 digits in a run and becomes `topic-<hash>`); a slug that differs from it (a model's) is scanned as it is, its hyphens counting as phone separators (`call-jane-555-1234567`, `call-jane-555-1234`, `555-1234-jane`), and its replacement, derive's slug, is then scanned the derive way. 3 and 4 digits typed with a space between them are no phone number in the typed text, the name or the id alike: they cannot be told apart from "Fortune 500 2026" or "Boeing 737 2026"; a proposed term that matches them is withheld; the reason says what was replaced and how many terms were withheld, never their text. Code: `topics._resolve_one`. *Host labels in any script, the ideographic full stops, the phone separators and the 9-digit rule, and the scan of the web app's key (2026-10-26, closing round 1; the 9-digit rule without its "2 or more groups" condition since closing round 2, which superseded it on 2026-10-26) were proposed by Claude Code; so were the checks of a proposed row (the name in closing round 2, widened to the id and the terms in closing round 3, 2026-10-26); so was the boundary of the local number (closing round 4, 2026-10-26); so were the scan of derive's slug with its hyphens read as spaces and the rule that 3 and 4 digits typed with a space are no phone number (closing round 5, 2026-10-26); they stand until Yelysei confirms or replaces them. Superseded 2026-10-26 (closing round 5): every proposed slug, derive's own included, was scanned as it is, its hyphens counting as phone separators (closing round 3), which with the closing-round-4 local number gave "Fortune 500 2026" the id `topic-<hash>`.*
  - **Matching, in order:** (1) the key equals the key of an existing topic's name or slug → that topic (`existing`; a retired topic → `needs_review`); (2) collection gives a headline made of the typed text to the first active topic whose terms match it (whole words, collection order: `first_topic_match`); when every word of the request key is in that topic's name, slug or matching terms → that topic (`existing`): "war in Ukraine", "immigration", "tariffs on China"; when only a later matching topic covers the words → `needs_review` naming both ("AI chips export controls": ai-regulation-export-controls covers it, but the older tariffs-trade-war-china gets the headline through "export controls"); (3) otherwise a new row is proposed, and it is `new` only when no earlier topic gets a headline made of the typed text, or of the typed text with one of its words in its other number (collection does not stem: "ICE raid" against immigration-southern-border's "ICE raids", "Government shutdowns" against "government shutdown", "Semiconductor" against "semiconductors"; the subject's documents would split between two topics). When one does — a rewording ("climate change", "Russian invasion of Ukraine"), a narrower topic ("Ukraine peace talks", "ICE raids in Los Angeles") or a shared word ("nuclear plant shutdown in Germany") — the request is `needs_review` with the proposed row and that topic, and the operator maps the request there or accepts the row: collection gives every shared document to the earlier topic, so the row would never receive the headlines that say the reader's own words and would fill with unrelated ones ("peace talks" about Gaza). Requests with the same key are resolved together: every distinct typed text of the key is checked as a headline in NFKC form, and the row is proposed from the most-requested one (ties in input order). When created_at of the existing topics is not readable, a reason that depends on which of two matching topics is older says so. *Rule (2) as a whole — the headline match, its coverage condition and the check against collection's first match — and the `needs_review` condition of (3) were proposed by Claude Code on 2026-10-26 after review rounds 1 and 2 (a single shared term sent unrelated requests to another topic's edition; a request was mapped to a topic that never receives its headline; rewordings and narrower topics became rows without their own documents); they stand until Yelysei confirms or replaces them. The other-number check of (3) was proposed by Claude Code in closing round 1 (2026-10-26), to the same standing.*
  - **Overlap rule for a new row:** a proposed term that breaks the term rules of `topics.normalize_term` (a stopword, a single word under 4 letters, …) is dropped as too generic; every other term that equals, whole-word-contains or is whole-word-contained in a term of an existing active topic (or of a row added earlier in the same batch) is flagged with that topic and dropped. The request is `needs_review`, not `new`, when no term could be derived, when every term is too generic ("us", "WHO", "May", "F-35"), when every term overlaps ("AI"), when an earlier topic gets a headline made of the typed text or of the typed text with one word in its other number (`topics.plural`, or a final s, es or ies→y removed; matching rule 3), when the overlap dropped a term that occurs in the typed text and no kept term occurs in it ("China" keeps only "chinas"), or, for terms derived from the phrase itself (dry run, dry-run stand-in, fallback), when no kept term occurs in the typed text ("चीन" split at its vowel sign into "च न"). A dropped term that an earlier topic holds only inside a longer term does not send the headline there, so with a kept term that matches the row stays `new` ("China chess": "china" is inside "china tariffs", "chess" collects the headline). A row whose terms translate or paraphrase the typed words ("Wahlen in Deutschland" → "German election") and overlap nothing is `new`. Derived terms come from the NFKC form of the phrase, and a hyphenated word stays whole ("K-pop", "X-ray"), its significant parts added as single words. A row whose terms are derived from the phrase (dry run, dry-run stand-in, fallback) keeps its status but carries a `caution` in mapping.json and report.txt, naming the single-word terms that a phrase of two or more words gave: such a word collects every headline that says it ("texas" of "measles outbreak Texas": 19 rehearsal titles and leads, none about measles; "TODAY" of "THE NEWS TODAY"); rows.sql then opens with `-- DO NOT APPLY WITHOUT REVIEW` and marks each such row. Whether derived rows should instead drop or gate those single words is Yelysei's call, since derive's term list is his decision of 2026-10-25. *These `needs_review` conditions were proposed by Claude Code on 2026-10-26 after review rounds 1 and 2, the `caution` marking in closing round 1; they stand until Yelysei confirms or replaces them.*
  - **Topic rows are insert-only:** `INSERT … ON CONFLICT (id) DO NOTHING RETURNING id`, never an upsert ("Russia Ukraine war" slugs to the seed's id); a taken id gets a numeric suffix (`-2`); every new id holds collection's rule `^[a-z0-9][a-z0-9-]{0,63}$` (a proposed slug over 60 characters is cut at a hyphen, one long word becomes `topic-<hash>`). New rows go in most-requested first, one autocommitted statement each, so they follow every existing topic in collection order. Changing an existing topic's terms is a deliberate UPDATE by its owner.
- **Edition cut** stays 05:30 America/New_York per date (09:30Z until the end of daylight saving on 2026-11-01, 10:30Z after), converted per date in code.
- **Delivery time** is a local time of day the user chooses; at that time the already published version of the day's edition is shown. It is not the time a run starts.
- **Where runs execute and who starts them.** The reasoning run for a date starts after the cut on the owner's machine (manual command or a local scheduler), one run per topic; a public VPS runs neither reasoning nor collection; model credentials live only in the owner's local `.env`. The web application never calls the models itself: it reads published versions from the store and writes nothing paid. Paid runs follow the per-account budget rules in reasoning/README.
- Why: the per-request cost and the per-account model limits make an unattended trigger from the web a budget and key-exposure risk; the owner-started run keeps credentials and spend under one person's control while users still get their editions at their chosen time.
- **Edition status files** (agreed with the portal in Issue #2 6411408519 and 6411653104, 2026-10-26): reasoning's edition runner writes one status file per topic and edition date, `<status-root>/<topic>/<date>.json`, with exactly the fields `topic`, `date`, `state` (`queued` | `running` | `published` | `failed` | `waiting_for_key`), `run_id`, `started_at` (the first live start of the run; until one, so with `attempts` 0, for example `waiting_for_key` before any start, when a live invocation of the runner first queued it; never a plan run's time), `updated_at`, `attempts` and `reason` (a short text or null), and `<date>.json.sha256` beside it (the sha256sum line of the file's bytes). Only a live invocation writes them: a plan run (no `--live`) writes none, so a topic-date without a file reads like `queued`; and while the snapshot store's newest version of the topic-date belongs to another run id (an earlier attempt), the file stays `published` with that run id until the new run publishes, so readers never see `queued`, `running` or `failed` next to an edition they can read. The deploy owner installs them into `QUORUM_STATUS_ROOT` with a `reasoning_status --file --sha256` command of the same shape as `reasoning_snapshot`; no upload endpoint. How the portal words each state for readers is the web's (Issue #2 6411408519, item 4). Anything else the runner keeps stays in its own records, never installed (reasoning/README.md › Daily editions). Why: the web never calls the models and has no endpoint for statuses, yet a reader of a typed topic needs to see whether its edition is coming; the portal reads only known fields, so the file holds nothing more.
