# Reasoning block

The LangGraph graph that turns one day's collected documents for one topic into verified stories, a roundup and a snapshot for the portal. Design: [docs/ARCHITECTURE.md](../docs/ARCHITECTURE.md). Product rules it implements: [docs/DECISIONS.md](../docs/DECISIONS.md) (handling facts, impact bar, stories as articles). Owner: Yelysei, branch `yelysei/agents`.

## Run it

```bash
cd reasoning
python -m venv .venv && . .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"

# dry run: fixture corpus, deterministic stand-ins for every model call, no credits spent
python -m quorum_reasoning.run --topic russia-ukraine-war --date 2026-10-22 --dry-run

# live model on the fixture corpus: tries the prompts and the JSON parsing before collection has data
python -m quorum_reasoning.run --topic russia-ukraine-war --date 2026-10-22 --model live --corpus fixture

# live run: the day's documents through Zetaris, Nemotron via the route in ../.env; checkpointed and journalled under --out
python -m quorum_reasoning.run --topic russia-ukraine-war --date 2026-10-23 --model live --corpus zetaris --out snapshots/_private
# continue a live run that died mid-way (same topic, date and --attempt): from the last completed node, ledger restored
python -m quorum_reasoning.run --topic russia-ukraine-war --date 2026-10-23 --model live --corpus zetaris --out snapshots/_private --resume

python -m pytest                                      # rules + end-to-end dry run
python -m quorum_reasoning.run --mermaid              # the graph as Mermaid (docs/ARCHITECTURE.md § 5)
langgraph dev                                         # LangGraph Studio on the same graph
```

`--verbose` prints every live model call as it happens (task, lane, the model that answered, milliseconds); without it the trace rows still appear as each node finishes. The summary line `answered by:` counts which models actually answered during the run — the same counts are in the snapshot under `provenance.answered_by`.

Run time on the NVIDIA direct route: at the 2400 ms base interval of the default lane a run of about 1 300 calls spends about 55 min on pacing alone, and with many HTTP 429s (each one doubles the route's interval for a while and two in a row add a 150 s pause) it can exceed 2 h. Three consecutive calls refused on one route stop the run with exit code 3 (`refusing to continue: route … refused 3 consecutive calls`); after such a stop, or after a stricter-state episode of long refusals, wait a few minutes before `--resume`. A resumed run answers the calls its journal already holds from the journal (replay, no credits, no pacing) and goes live for the rest.

Nightshift notes, learned the hard way: lanes have duties (Race, Judge, Verify, …) and chat requests go to Race lanes; `meterless/fast`, `meterless/deep` and `meterless/judge` are dispositions ranked over the lanes, not pins, and on 1.2.3 all of them answer from the Lightning lane for small tasks. On v1.2.2 an explicit `nvidia/...` id could be substituted by whatever lane was ready; on **1.2.3** the explicit id `nvidia/nemotron-3-ultra-550b-a55b` selected Ultra in every observed request (Vadim's METERLESS-ROUTING-01, 2026-10-23, five receipts) — so through Nightshift the fact-checker lane is pinned with the explicit id, the default lane stays `meterless/fast`, and `--test-connection` must show both before a run. The response proves which model answered, not that a Verify-duty lane ran. Treat `provenance.answered_by` and the per-call `receipt_id` in the ledger — not the route in `.env` — as the evidence of which model powered a run; Nightshift's Console › Proof holds the receipts. The Windows runtime listens on Windows loopback `127.0.0.1:8088` only: a WSL2 client under NAT cannot reach it, so a Nightshift run is started from a Windows Python venv (`.venv\Scripts\activate` in `reasoning/`) unless Yelysei approves a WSL networking change (mirrored networking per `docs/wslconfig.proposed`, or a port proxy).

`--fixture usecases/quiet_day` (or `QUORUM_FIXTURE`) picks another bundled day for `--corpus fixture`; the use-case days under `fixtures/usecases/` are the ones `tests/test_usecases.py` asserts on.

Two independent switches: the model axis (`--model dry|live`; `dry_run` in the state; `QUORUM_DRY_RUN=1` or a missing key forces dry) and the corpus axis (`--corpus fixture|zetaris`; `corpus` in the state; defaults to fixture when the model is dry, zetaris otherwise). `--dry-run` is the shortcut for dry + fixture.

In Studio the input form has five fields: `topic_id`, `edition_date`, `dry_run` (switch it on unless you mean to spend credits), `corpus` (fixture or zetaris) and an optional `run_id`. Submit with the first two empty and `plan` stops with a message saying so. The yellow "LangSmith API key is missing" banner is expected: tracing to LangSmith stays off (ARCHITECTURE.md § 9); the run's own trace is the `steps` list in the state. The **Deploy** button pushes the graph to LangChain's hosted platform (LangSmith Deployment); we do not use it — the graph runs on our own host.

Output: the snapshot is stored as the next immutable version `snapshots/<topic>/<date>/v<N>.json` (git-ignored; `latest.json` beside it; `python -m quorum_reasoning.run --list` and `--show --topic … --date … [--version N]` read the store) and the trace is printed as a table; a live run also writes the private call ledger `v<N>.ledger.json` next to its version (never into the snapshot). `python scripts/regenerate_samples.py` rebuilds the three committed `docs/examples/snapshot.*.json` after any change to the snapshot shape. A committed copy of the dry-run output is `docs/examples/snapshot.sample.json`, the test dataset for the portal. Exit code 2 when the snapshot is `partial` (a node recorded an error).

Environment, all read from the repo-level `.env` (see `.env.example`): `MODEL_BASE_URL`, `MODEL_API_KEY`, `NEMOTRON_MODEL` (or the `METERLESS_*` names) for the model — the Nightshift URL and Runtime token from its Console, never the NVIDIA key, which lives in Nightshift's Providers tab; `NEMOTRON_MODEL_FACT_CHECKER` for the second lane; `python -m quorum_reasoning.run --models` lists the routes the hotspot offers and `--test-connection` shows which model answers on each lane; `ZETARIS_REST_URL`, `ZETARIS_ORG_ID`, `ZETARIS_API_KEY` for the corpus; `ZETARIS_COLLECTION_DB` when the Lightning database is not `QUORUM_COLLECT`; `COLLECTOR_USER_AGENT` for fetching article text; `QUORUM_COLLECTORS_PATH` pointing at a checkout of the `data-collection` branch when `collectors/` is not in this tree (the trace's `plan` row says which fetcher is in use; the fallback fetcher is for development only, never for evidence); `QUORUM_MIN_INTERVAL_MS` to override the pause between live calls (`QUORUM_MIN_INTERVAL_MS_FACT_CHECKER` / `_REVIEWER` per lane; the pause is kept per model route — decision in `llm.min_interval_ms`); `QUORUM_DRY_RUN=1` to force the dry run. With no model key configured the graph runs dry on its own.

## Layout

```
reasoning/
  langgraph.json              what `langgraph dev` loads: quorum_reasoning.graph:graph (module path; see Decisions)
  config/reasoning.toml       thresholds, caps, loop limits, forbidden words, model routes
  quorum_reasoning/
    graph.py                  StateGraph assembly, conditional edges, run_local(), mermaid()
    state.py                  RunState, DocRef, Claim, Evidence, Event, Rubric, StepRecord
    nodes/                    one file per node, each `run(state) -> partial state`; routes next to their node
    rules/                    confirmation.py, impact_bar.py, writing_rules.py — pure, unit-tested
    tools/                    corpus.py (Zetaris SQL or fixture), fetch_text.py (access levels, robots.txt)
    prompts/                  one Markdown system prompt per model task
    dryrun.py                 deterministic twin of every model task
    fixtures/sample_day.json  fictional corpus for the dry run and the tests
    store.py                  the snapshot store: immutable versions per topic-day, latest.json, the ledger beside it
    trace.py, ids.py, text.py, llm.py, config.py, run.py
  tests/                      test_rules.py (rules), test_graph.py (end-to-end dry run, escalation, Mermaid), and one file per
                              2026-10-23/24 work item (red team, injection, use cases, live guards, provenance, reviewer, store)
```

Nodes: `plan → cluster → score_importance → extract_claims → research ⇄ verify → fact_check → adjudicate → (review_disputed →) (escalate →) frame → write ⇄ critique → roundup → publish`. Every node appends a `StepRecord` (node, iteration, event, decision, reason, model, duration); a loop shows as the same node with a higher iteration. The snapshot carries the whole trace.

## What a dry run shows

On the fixture day the trace shows every mechanism the architecture promises: a second research round for thin claims (`research` iteration 2, `verify` iteration 2), a blind fact-checker whose verdict differs from the verifier's on one claim and a third blind pass that sides with the chain holding the evidence (`review_disputed`; all three verdicts kept on the claim), the critic rejecting a planted forbidden word in draft 1 and approving draft 2, two stories above the bar and two events in the roundup with their evidence status. The texts themselves are stand-ins; the real articles come from the model.
